# 第二轮性能优化与上线边界（2026-10-10）

## 1. 结论

当前慢感由两部分叠加：Cloudflare Quick Tunnel 的随机域名、DNS/TLS、边缘节点和本机上行链路会增加且波动公网首访时间；与此同时，旧版首页大图、首次路由分包和后端列表 N+1 查询属于应用自身问题，正式上线后仍会存在。本轮已修复应用侧问题，但 Quick Tunnel 仍只适合临时测试，不能作为生产性能结论或正式发布方案。

## 2. 已实施优化

- 首页 `campus-stories.png` 原文件 2,710,792 B，改为 WebP 响应式四档：640 宽 131,950 B、800 宽 184,872 B、960 宽 255,534 B、完整宽 554,086 B。浏览器按视口选择，不再统一下载原始 PNG。
- 三张类别示意图由每张约 1.8–2.0 MB 改为 33–52 KB WebP，并继续使用懒加载与异步解码。
- 首页组件进入主包，省去首次访问 `/home` 的额外路由分包往返；其余重型图表和 3D 模块仍保持懒加载。
- 浏览器空闲时预取顶部常用路由，并预热招领、遗失和地图聚合三个公开接口；启用节省流量时不预取。
- 新增 30 秒、按校区隔离的公开 GET 内存缓存，并合并同时发生的相同请求。登录、发布、审核等写操作和校区切换都会清空缓存，不缓存私密业务响应。
- 顶部当前校园名称写入本机缓存，刷新时立即显示；后台目录查询仍会异步校验并更新。
- 物品列表把 `location → campus → school` 改为一次联表读取，消除随列表条数增长的 N+1 查询；新增最多 7 条 SQL 的回归门禁。
- Django 启用 GZip 中间件，压缩符合条件的 JSON 响应。
- 公网预览对带内容哈希的 `/assets/` 使用一年不可变缓存，对稳定命名的 `/local-assets/` 使用一小时浏览器缓存；HTML 与 API 不做长期缓存。
- 修复本地 `start.ps1` 在 Windows PowerShell 5.1 下因 UTF-8 中文字符串被错误解析而无法启动的问题。

## 3. 本机测量基线

测试环境为 Windows 本机回环地址，不代表公网 SLA：

| 对象 | 实测范围 |
| --- | --- |
| Vite 首页 HTML | TTFB/总耗时约 17–61 ms |
| 960 宽首页 WebP | 255,534 B，约 2–3 ms |
| 经前端代理的物品列表 API | 约 16–39 ms |
| 直连 Django 的物品列表 API | 约 11–33 ms |
| Playwright 首页、列表、截图及隐私响应代表性流程 | 约 1.5 s |
| 当前 Quick Tunnel 首页 HTML | 热连接约 1.07–1.12 s，冷连接约 4.01 s |
| 当前 Quick Tunnel 物品列表 API | 约 1.21–1.58 s |
| 当前 Quick Tunnel 最终默认 185 KB 首页图 | 约 2.85–6.65 s |

本次公网节点由响应头和隧道日志显示为 Cloudflare LAX，`CF-Cache-Status` 为 `DYNAMIC`；节点、线路和结果都可能变化。对照结果说明本机应用没有“数秒才响应”的固有瓶颈，而当前公网首访的主要延迟来自临时隧道和访问者网络。预览缓存头会在下次重启公网测试后生效；固定部署仍需采集 Web Vitals 与 API P50/P95 后再验收。

## 5. 正式上线建议

正式发布不应继续使用随机 Quick Tunnel。建议使用固定域名、HTTPS、CDN 静态缓存、Nginx/Caddy 或云负载均衡代理静态前端与 Waitress/Gunicorn 后端，并为 MySQL 配置备份、监控和连接池。上线后至少持续采集 LCP、INP、CLS、静态资源命中率、API P50/P95/P99、错误率与慢 SQL；本轮本机数据只能作为开发基线。
