# 13 正式生产部署

## 1. 部署目标

正式生产环境使用固定域名和独立云服务器，不使用 Cloudflare Quick Tunnel。推荐最低配置为 2 vCPU、4 GB 内存、80 GB SSD、Ubuntu 24.04 LTS，并选择云厂商提供明确实例 SLA 的地域与规格。若面向中国大陆用户且域名解析到中国大陆服务器，必须先完成 ICP 备案；香港、新加坡等境外地域通常不要求 ICP 备案，但访问时延与数据合规边界需要单独评估。

生产链路为：

```text
固定域名 DNS -> 云服务器 80/443 -> Caddy 自动 HTTPS
                                  -> Vue 生产静态资源
                                  -> Django/Waitress 内网服务
                                  -> MySQL 8.4 内网数据库
```

MySQL、Django 与数据卷不映射公网端口。Caddy 自动申请和续期证书，Docker Compose 负责服务健康依赖与异常自动重启。

## 2. 服务器准备

在云平台完成以下配置：

1. 创建具备实例 SLA 的 Ubuntu 24.04 LTS 云服务器，绑定固定公网 IP。
2. 安全组仅放行 TCP 22、80、443 和 UDP 443；数据库 3306 不放行公网。
3. 将固定域名的 A 记录指向服务器公网 IP，等待解析生效。
4. 安装 Docker Engine 与 Docker Compose 插件。
5. 将项目上传到服务器，例如 `/opt/campustrace`。

购买实例、域名、固定 IP 或其他计费资源前，应由资源所有者确认云厂商、地域、规格、期限与费用。

## 3. 生产环境变量

复制环境变量模板并只在服务器填写真实值：

```bash
cd /opt/campustrace
cp deploy/.env.production.example deploy/.env.production
chmod 600 deploy/.env.production
```

必须替换 `DOMAIN`、`DJANGO_SECRET_KEY`、`MYSQL_PASSWORD` 与 `MYSQL_ROOT_PASSWORD`。域名需要同步写入 `DJANGO_ALLOWED_HOSTS` 与 `DJANGO_CSRF_TRUSTED_ORIGINS`。高德地图密钥若启用，必须配置生产域名白名单。

`deploy/.env.production` 包含密钥，不得提交版本库、发送到群聊或写入答辩材料。

## 4. 首次发布

```bash
docker compose -f docker-compose.prod.yml build --pull
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml ps
./deploy/healthcheck.sh https://你的固定域名
```

后端容器启动时会自动执行数据库迁移、静态文件收集和 Django 生产检查。正式环境默认不导入固定演示账号与 360 条合成数据。

创建首个管理员时使用交互式命令，不要把管理员密码写进脚本：

```bash
docker compose -f docker-compose.prod.yml exec backend python manage.py createsuperuser
```

## 5. 发布更新与回滚

更新前先备份，再构建新镜像：

```bash
sh deploy/backup.sh
docker compose -f docker-compose.prod.yml build --pull
docker compose -f docker-compose.prod.yml up -d
./deploy/healthcheck.sh https://你的固定域名
```

代码版本应打 Git 标签。回滚时检出上一稳定标签并重新构建；涉及数据库结构的回滚必须先验证迁移兼容性，不直接删除生产卷。

## 6. 备份与监控

`sh deploy/backup.sh` 先导出数据库，再压缩、验证媒体包和 SHA256 校验，全部成功后才发布 `backups/backup-时间-进程号/` 目录并清理超过14天的完整备份。失败不会发布半份备份或清理已有备份。旧版平铺备份文件保留，需人工迁移。

使用 `sh deploy/verify-backup.sh backups/backup-时间-进程号` 验证恢复：检查校验和、导入隔离的临时数据库并解压媒体，结束时删除临时数据库，不覆盖业务库。正式容器环境首次部署后及每季度执行。备份应同步至其他故障域；数据库事务快照与媒体打包并非跨存储原子快照，严格一致的恢复点需安排暂停写入窗口。

监控至少覆盖：域名 HTTPS 可达性、`/api/v1/health/`、CPU、内存、磁盘、容器重启次数、MySQL 容量、证书续期和备份任务结果。告警接收人与响应时间必须在试点前确定。

## 7. SLA 边界

网站可用性受云服务器、网络、DNS、证书、应用和数据库共同影响。云厂商实例 SLA 只覆盖其合同定义的基础设施范围，不自动等同于 CampusTrace 端到端 SLA。对外承诺前应记录所选云产品的正式 SLA 条款，并配置至少每日备份、外部探测和故障响应流程。若要求跨可用区容灾或数据库独立 SLA，应把 MySQL 迁移到云厂商托管数据库，并部署至少两台应用实例和负载均衡。
