# 07 固定数据与评测设计

## 1. 数据合同

命令：`python manage.py seed_demo`。

- 唯一基准时间：`DEMO_BASE_DATE=2026-08-20T08:00:00+08:00`。
- 唯一随机种子：`20261007`。
- 24 个地点（主校区 + 23 个功能区）、4 个服务站。
- 180 条遗失、180 条招领，覆盖 6 周。
- 100 对合成正例，按 60/20/20 划分 TRAIN/VALIDATION/TEST。
- 全部演示物品 `is_demo=True`，全部基准 `is_synthetic=True`，文档和界面不得将其包装成真实校园统计。

命令完成前会验证五项精确数量，不满足合同则事务回滚。重复执行不会静默删除数据，必须显式使用 `--reset-demo`。

## 2. 比较方案

- B0：词/集合重叠，仅作低成本对照。
- B1：标准 TF-IDF + 余弦相似度。
- B2：TF-IDF + 余弦 + 六因子初始权重。
- B3：验证集选择后的校园别称、缺失感知与融合参数。

至少进行去地点、去时间、去结构化属性、去别称中的三项消融。所有方案必须使用相同的查询、候选、标注、时间快照与指标代码。

## 3. 指标与防泄漏

报告 Precision@K、Recall@K、Hit@K、MRR，并给出分母、候选资格召回损失与置信区间（样本足够时）。认领批准/完成状态不是训练标签；人工标注与合成规则必须注明来源。权重选择只看训练/验证集，测试集仅用于最终一次报告。

## 4. 当前已运行证据

命令：`python manage.py evaluate_demo`，输出：`artifacts/experiment-results/demo-benchmark.json`。

- 数据划分已校验为 60/20/20，测试查询 20 条，候选 121 条，候选资格召回率 1.0。
- B3 只用 VALIDATION 的 MRR 在三组预注册权重中选择；三组都为 1.0，因此按确定性规则选择 `balanced`，不声称它显著更优。
- 当前 B0、B1、B2、B3 在合成 TEST 上均为 Hit@1=1.0、MRR=1.0；四组消融也未拉开差距。这说明当前合成正例过于容易，只能证明评测链路可复现，不能证明六因子比基线更优，更不代表真实校园准确率。
- 后续必须增加匿名化人工判定的困难负例和别称/缺失/冲突样本，才能用于参数选择与申报效果结论。
