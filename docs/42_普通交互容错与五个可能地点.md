# 普通交互容错与五个可能地点

完成日期：2026-11-17。

## 原因

普通聊天曾和严格的规划 JSON、业务字段提取绑定。一个引用、类型或字段不合规就会导致整轮对话报错；问候还可能成为没有类别的空草稿，随后错误地复用。仅测试固定六句话不足以发现这些问题。

“卡面有姓名、学号”是一般特征描述，不等于发送具体个人信息，不应中断对话。

## 通用改动

- 对话规划格式失败时，用原来的千问模型走独立的自然语言回复通道，不再只返回模板错误。
- 聊天使用逐字段核对：只保留能在用户原话中找到的类别、颜色、品牌、地点、外观短语。剔除未核实的字段，其他字段照常使用，不编造填空。普通表单的严格校验和实际写入校验继续保留。
- 不再用模型的 `facts_changed=false` 丢弃新证据，也不让空草稿占住后续物品。问候和没有实际物品特征的咨询不填入工作台。
- 明确更正按后文处理，已否定的旧颜色不继续作为确定颜色。缺失但此前已核对的字段可保留，避免补充一个特征就遗忘其他信息。
- 姓名、学号只记录“卡面印有这些信息”的标记；具体号码不进入公开文案。不通过单独的姓名学号话术分支模拟整段对话，仍由千问生成自然回答。
- 时间和地点仍由原话核对；不记得的信息不强迫猜测，不能改问“哪个楼栋”来反复索取已忘记的地点。

## 五个可能地点

小寻的发布核对界面复用普通表单的地点协议和地图组件：

- 遗失信息最多 5 个可能地点，可多选、移除和上下调整排名。
- 招领信息只保留 1 个拾获地点。
- 支持演示地图的结构化区域和真实地图的 GCJ-02 选点；两种来源不混用。
- 对外公开校区范围，具体候选使用 `location_candidate_ids` / `location_candidate_points` 提交。跨校区、重复、超限仍由原来的 `ItemSerializer` 拒绝。
- 用户没有说明或选择地点时不凭空生成五个地点。候选按用户选择的先后排序。

## 验证

- 真实对话 A：问候 → 丢学生卡 → 蓝色且地点不记得 → 有名字和学号。蓝色、类别和一般身份标记都保留，聊天不中断。随后可选择 5 个地点，尝试第 6 个被阻止，顺序可调整。
- 真实对话 B：不同问候 → 米白色帆布袋和猫图案 → 更正为米黄色 → 地点忘记 → 暂不发布 → 补充袋口打结、袋内有练习册 → 无照片和情绪求助。测试验证更正、新特征、主体保留及自然交流，不向演示库写入记录。
- 测试数据库验证：5 个候选的 ID 与排名真实保存，6 个被拒绝，招领的多个地点被拒绝，匿名详情不含受保护地点。
- 后端完整回归 172 项通过，后续对话/身份标记/公开文案定向 33 项通过（范围重叠）；前端 60 项通过、生产构建通过。

证据：`artifacts/xun-card-identity-audit.json`、`artifacts/xun-card-five-places.png`、`artifacts/xun-dialogue-variants.json`、`artifacts/xun-dialogue-variants.png`。

这些场景证明常见路径和错误恢复已验证，不代表任何自然语言表达都能百分之百理解。实际发布、认领及交接仍保留用户确认与权限校验。
