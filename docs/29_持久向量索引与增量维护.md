# 持久向量索引与增量维护

## 当前实现

ItemVector表按物品和模型身份保存向量、维度、公开内容哈希与更新时间。模型身份包括接口地址、模型名、AI_LOCAL_EMBEDDING_REVISION及公开文本格式版本。模型权重即使沿用同一别名，升级时也必须提高修订号并重启服务、预建新索引；不会自动辨认相同别名背后的权重替换。

不再依赖一小时内存缓存，也不再因候选超过500条而拒绝。仍采用MySQL持久向量与应用层精确余弦扫描，不是ANN向量数据库；会读取当前校区可见候选，数据量非常大时仍需进一步优化内存和搜索耗时。

## 内容变化与可见性

只用公开类别、品牌、颜色、标题和描述计算文本哈希。少量缺失或过期记录在检索中按16条一批补建，未改变记录直接复用；地点和时间不进入向量文本，重排时读取最新公开字段。

批量推理前重新检查资格，写索引时短事务锁定记录并核对哈希；编辑或撤回发生在推理期间就丢弃旧向量。返回候选前再次查询校区、审核、业务状态和内容哈希。物品删除时由外键级联删除索引。撤回后已有向量可能仍保留在表中，但不会参与公开检索，且不会作为公开旧快照返回。

没有在发布事务或model.save中同步调用模型，也未创建后台定时索引任务。增量更新通过检索时少量补建及管理员维护命令执行，不应宣称发布后已自动完成后台索引。

## 冷启动与维护

网页默认最多同步补建32条（AI_INDEX_SYNC_LIMIT）。超过该数量返回503，错误码ai_index_pending，避免用户请求承担整库编码。此响应不意味着存在后台建索引任务，运维需主动执行预建命令。

在backend目录执行：

```powershell
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe manage.py build_ai_index --owner admin_demo --campus-code demo-campus --limit 256
```

owner必须是现有有效管理员；正式环境使用正式管理员账号。可加 --kind LOST或FOUND；默认ALL。命令也受全局AI并发准入和90秒总预算约束，不会与网页任意并行占用模型。limit限制本次补建条数，超时前已写入的批次保留，可重跑续建。remaining=0表示该次扫描时无需再补建，不保证运行期间没有新的内容变化。

旧模型版本向量保留以便明确区分版本，不会被混用。正式部署需制定旧版本清理与数据库备份策略。首次上线及变更模型修订号后，应在开放检索前执行维护命令，避免网页首次请求报索引未就绪。

## 验证

测试覆盖超过500条已索引记录、跨缓存复用、描述更新、模型修订变化、批量缺失保护、推理中撤回与并发编辑。真实本地模型已为演示校区241条公开记录建立索引，物品与认领数据不改动。

本轮后端全量120项测试通过（148.19秒）。新进程再次维护返回eligible=241、already_current=241、built=0、remaining=0。网页服务重启后真实照片寻物浏览器验收通过（21.7秒）。Django检查通过，无遗漏迁移。当前为精确扫描索引，不将此结果解释为大规模ANN性能或真实校园找回率。
